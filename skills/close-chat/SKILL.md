# close-chat — закрытие сессии по чек-листу

Скилл проводит сессию через четыре фиксированных шага в конце работы: убедиться, что нет подвешенных вопросов, проверить changelog, убрать мусор, закоммитить только то, что было сделано в этом чате.

**Принцип:** быстро прогнать пайплайн с минимумом вопросов. По умолчанию коммитим только то, что трогали в этом чате (touched). Чужие изменения не коммитим. Вопрос пользователю — **только** если без него нельзя достоверно определить принадлежность файла к сессии или если есть реальный блокер. Сомнение само по себе — не повод спрашивать; если файл уверенно touched — включаем в коммит без вопроса. Никаких автоматических удалений за пределами явного whitelist.

Caveman-режим на подтверждениях ослабляется: вопросы и предупреждения писать нормальным русским.

## Когда вызывать

- «/close-chat», «/close_chat», «закрыть чат», «закрытие сессии», «конец чата», «заверши сессию»
- Пользователь явно намекает на финал работы и просит привести репозиторий в порядок перед уходом

Не вызывать автоматически в фоне — это всегда взаимодействие с пользователем.

## Аргументы

- Без аргументов — полный пайплайн интерактивно.
- `--dry-run` — показать план по каждому шагу, ничего не менять и не коммитить.
- `--skip 0|1|2|3` — пропустить указанный шаг (можно повторять: `--skip 0 --skip 2`).

## Подготовка

Перед шагом 0 собрать **touched-список** — файлы, которые агент сам создавал/редактировал в этой сессии (по памяти о tool calls Write/Edit и созданным untracked). Сюда же — файлы, которые в `git status` появились/изменились в ходе этой сессии и логически связаны с её темой (например, артефакты touched-скриптов). Если файл уверенно touched — относим к touched без вопроса. Помечать «неоднозначно» только если действительно нет признаков принадлежности к сессии.

## Шаг 0. Открытые вопросы

Цель шага — поймать реальные блокеры, не превращать его в допрос. Если блокеров нет — одна строка «открытых вопросов нет» и сразу шаг 1.

Источники (просканировать молча):

- TodoWrite-список сессии — пункты `in_progress` / `pending`.
- История чата — только **явно подвешенные** вопросы пользователю, на которые он не ответил.
- `CHANGELOG.md` — незакрытые TODO в `[Unreleased]` (если агент сам их оставлял).

Действие:

- Если ничего не найдено — сказать «открытых вопросов нет», шаг 1.
- Если нашлось — собрать **один** компактный список и задать **один** общий вопрос: «доделать сейчас / оставить заметку для следующей сессии / закрыть как есть».

Не переходить к шагу 1, пока есть нерешённые блокеры из ответа пользователя.

## Шаг 1. Changelog

Если сессия меняла поведение CLI, MCP, API, установку или другой user-facing surface — проверить, есть ли запись в `CHANGELOG.md` под `## [Unreleased]`.

- Уже есть релевантная запись → одна строка «changelog ок», шаг 2.
- Нет, но изменения user-facing → предложить добавить пункт (формат — [release](../release/SKILL.md), секции `### Added` / `### Changes` / `### Fixes`). На `--dry-run` — только показать черновик.
- Только внутренний рефакторинг / тесты без смены поведения → «changelog не нужен», шаг 2.

Не коммитить changelog отдельно от остального touched на этом шаге — только подготовить текст; stage на шаге 3.

## Шаг 2. Очистка мусора

Сканировать `git status` (untracked + modified) **только по touched-списку**, классифицировать:

| Категория | Действие |
| --- | --- |
| **Whitelist** untracked: `tmp/`, `*.tmp`, `*.bak`, `*.orig`, `scratch_*`, `_tmp_*` | Удалить без вопросов, перечислить после |
| **Touched-черновики**: отладочные скрипты, одноразовые логи, явно созданные «на разок» | Удалить без вопросов, перечислить после |
| **Полезное будущим агентам** (заметки, незавершённые исследования) | Не удалять — упомянуть строкой, спросить: оставить в репо / вынести в отдельный файл / удалить |
| **Чужие untracked / modified** (не в touched-списке) | Не трогать — одна строка «вне скоупа сессии: N файлов» |

Перед удалением показать итоговый список «удалить:» и подождать **одно общее** подтверждение. На `--dry-run` — только показать список.

Спорные файлы (не whitelist, не явный черновик) — **не удаляем**, оставляем как есть, без вопросов.

## Шаг 3. Коммит изменений сессии

Базовая классификация по `git status`:

- **моё (touched)** — попадает в коммит автоматически, **без вопросов** (если пользователь не сказал «стоп» на шаге 0).
- **чужое** — файл в status, но не в touched → молча исключаем, в финальной сводке: «оставлено вне коммита: N файлов».
- **неоднозначно** — агент **не может** определить принадлежность к сессии. Только такие файлы — повод для уточнения.

### Порядок действий

1. Классифицировать touched. Показать **короткий** итог: «к коммиту: N файлов», «вне: M файлов».
2. **Дробление на несколько коммитов — по умолчанию НЕТ.** Один коммит на всё touched. Дробить только если в touched **явно** смешаны несвязанные темы (например, feat + несвязанный fix). При срабатывании — один короткий вопрос: «один коммит или N по темам?».
3. Если есть «неоднозначно» — **один** общий вопрос со списком: «включить в коммит / оставить вне / удалить». Если нет — переходим к коммиту **без подтверждения состава**.
4. Stage: `git add <path>` по каждому touched-файлу. **Не** `git add -A`, **не** `git add .`.
5. Сообщение — Conventional Commits, subject ≤50 chars (см. `.agents/skills/caveman-commit/` если установлен). Затем `git commit` с HEREDOC. Коммит — **только после явного «да» / «коммить»** от пользователя на этом шаге.
6. Не пушить (push — только по явному запросу).

На `--dry-run` — только показать классификацию и предполагаемое сообщение, не коммитить.

**После коммита (опционально, одной строкой):** если менялся `src/`, напомнить `pnpm test` или `npx vitest run test/` — не запускать автоматически.

## Что скилл НЕ делает

- Не пушит в remote.
- Не запускает `qmd collection add`, `qmd embed`, `qmd update` (индекс — вручную).
- Не трогает `~/.cache/qmd/index.sqlite`.
- Не трогает untracked вне whitelist и вне touched-списка.
- Не режет релиз (`/release` — отдельно).
- Не каскадит при обрыве: если пользователь сказал «стоп» — остановиться, ничего не откатывать.
- **Не задаёт лишних вопросов.** Каждый вопрос оправдан: блокер (шаг 0), удаление (шаг 2, одно подтверждение), неоднозначная принадлежность (шаг 3), явное «коммить?» перед `git commit`.

## Границы

- Коммит — только по явному подтверждению пользователя.
- Удаление файлов — whitelist автоматически; всё прочее — через подтверждение.
- Если в сессии вообще не было правок — шаги 1–3 пропустить, сказать «коммитить нечего».
